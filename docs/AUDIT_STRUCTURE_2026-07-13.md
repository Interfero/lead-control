## 1. Вердикт одной фразой

Проект **не разваливается** — это рабочая операционная CRM среднего размера (MVP+, выросший в прод).  
Но это **ещё не зрелая платформа** под рост на ~80 городов и отчёты «за секунды». Технический потолок уже рядом.

## 4. Где реальные костыли и проблемы

Не «всё — костыль». Долг **сконцентрирован** в нескольких зонах.

### 4.1. Отчёты — самое опасное

Паттерн: цикл по городам → `Order::…->get()` → агрегация в PHP (`ReportController`, `CityReportService`).

- На малой истории терпимо.
- На десятках городов + накопленной истории — минуты, таймауты, деградация.
- Материализованных срезов (`report_city_daily` / stale / ночной job) **нет**.

Это потолок продукта, не баг вёрстки.

### 4.2. География — исключение «Н. Новгород»

- В модели есть `parent_city_id` для всех городов.
- `City::operationGroupIds()` по сути разворачивает кластер **только для Н. Новгород + спутники**.
- Авто-спутник 50/50 дополнительно ловит имя города через `str_contains` в комментариях/улице — типичный «пока работает» костыль.
- Дзержинск работает; обобщённой модели «спутник = бизнес-правило для любого материнского города» нет.

### 4.3. Атрибуция звонков (критичный продуктовый костыль)

- Справочник `sources` с телефонами, kind, import — есть.
- `MangoCallService` мапит линии из **`.env`** (`MANGO_LINE_1/2/101_SOURCE_ID`), а не по `sources.source_phone`.
- Новая боевая линия = правка конфига, а не справочника.

### 4.4. Двойной фронт и деплой

- Layout грузит и `public/css/app.css`, и Vite (`resources/css/app.css` + JS).
- `vite.config` отсутствует — воспроизводимость сборки слабая.
- Деплой: SCP/FTP на shared REG.RU. Жить можно; масштабировать и hardening — тяжело.
- Очередей нет → async outbound / тяжёлые отчёты на shared ограничены.

### 4.5. «Временное навечно»

| Что | Факт |
|-----|------|
| Модуль `prom.*` | Роуты есть, в меню «временно отключено» |
| Статусы `waiting_parts` / `waiting_payment` | Ещё в отчётах и доступности мастера |
| Валюта в CFM-комментариях | Осталось **«тг»**, в UI — рубли |
| Prune-команды | Несколько overlapping (`orders:prune-test-data`, `db:prune-production-test-data`, `app:prune-test-environment`, `orders:prune-seed-not-processed`) |
| Фильтры списка заказов | Сессионное восстановление — хрупкий паттерн (частично уже чинили) |
| Роли | Матрица через копипасту `hasAnyRole([...])`, без Laravel Policies |
| Runtime `Schema::create` | Fallback создания таблиц логов активностей — foot-gun деплоя |

### 4.6. Что как раз не главный долг

Формулы ЗП мастера уже сведены в `OrderService` (`getMasterPercent` / `calculateMasterSalary`); `HrService` / `GmApiService` делегируют туда. Дублируются скорее **обёртки агрегации**, а не сам коэффициент.

## 5. Дополнительные риски модели и ops

- **Нет SoftDeletes** — удаления жёсткие (`DELETE`, prune).
- ENUM/string статусы + наследие миграций статусов.
- Партнёрские поля на `sources` + `orders.partner_user_id` — рабочие, но связность размазана.
- Security: shared hosting, `trustProxies(*)`, секреты в `.env`; GM secret может fallback’иться на `APP_KEY` — неудобная связка.
- Audit заказов есть (`order_activity_logs`), но это не полноценный compliance-журнал ПДн.
- Мониторинг (Sentry / Horizon / алерты) по сути отсутствует.
- `.env.example` отсутствует (onboarding/аудит секретов затруднены).

## 7. Сколько работы ещё предстоит

Оценки в **engineer-weeks** (≈ календарные недели одного сильного разработчика, знакомого с кодовой базой). Консервативно.

| Цель | Объём |
|------|------:|
| **Стабилизация без новых фич** (двойной CSS/конфиг, статусы, «тг», prune helper’ы, smoke-тесты, самый жрущий SQL отчётов без полной материализации) | **6–10 недель** |
| **ТЗ только этапы A + B** (DID → Source по телефону + срезы отчётов / инвалидация) | **8–14 недель** |
| **ТЗ A–F целиком** (UI/права, очереди, security/2FA/crypto PoC, VPS + мониторинг) | **30–50+ недель** |

Разбивка full-пакета (очень ориентировочно):

| Этап | Тема | Недели |
|------|------|-------:|
| A | Атрибуция звонков | 2–3 |
| B | Срезы отчётов | 6–11 |
| C | UI / права / телефоны | 2–4 |
| D | Outbound-очереди | 3–6 |
| E | Security hardening | 4–8 |
| F | VPS + мониторинг | 6–12 |

**Практичные сценарии:**

1. «Жить и чинить боли по мере» — ещё **месяцы точечных правок** без большого рефакторинга.  
2. «Довести до нормативов ТЗ» — **отдельный проект**, не хвост текущего спринта.  
3. Рациональный приоритет: **A → B → F**, параллельно лёгкий C; E/crypto не блокировать A/B на shared.

## 8. Рекомендуемый фокус (если выбирать три вещи)

1. **Атрибуция:** канон линии = `sources.source_phone`, `.env` только fallback → лог.  
2. **Отчёты:** убрать city-loop `get()`; затем срезы дня/города.  
3. **Опоры инженерии:** вернуть воспроизводимую сборку фронта, smoke-тесты на критичные сценарии, план ухода с shared.

Без этого скорость правок будет падать даже на мелких фичах (фильтры, мобила, спутники уже давали регрессии).
