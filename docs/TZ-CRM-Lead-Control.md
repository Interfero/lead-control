## 1. Цель продукта

Lead Control — операционная CRM выездного ремонта (ТВ/ПК и смежное), в которой:

1. Руководитель с большим числом городов открывает отчёты **за секунды**, а не за минуты.
2. По любому входящему звонку и заявке **всем ролям** (КЦ, дисп, дир, регдир, гендир) видно:
   - на какой **номер** позвонил клиент;
   - какая **рекламная кампания** привязана к номеру (имя на листовке / учётка Авито / партнёрский канал).
3. Заявки, касса, сотрудники, ОКК, справочники и API для GM/SuperPart работают стабильно.
4. Интеграции не тормозят UI и не имеют лишних прав.
5. Безопасность и ПДн — по §9, без «театра», который убивает скорость.

## 4. Диагноз as-is (обязателен к устранению)

### 4.1. Отчёты: алгоритм, а не «Laravel плохой»

В `ReportController` / `CityReportService`: цикл по городам → `Order::…->get()` → агрегация в PHP. На десятках/сотнях городов — минуты. Индексы есть, но не спасают от N×full-load.

**Живой факт 2026-07-11:** отчёт «По закрытым» на ~48 городах за июль при малом числе закрытий открылся быстро. Это значит «пока терпимо на малой истории», а **не** «алгоритм ок». Критерий приёмки — фикстура ≥80 городов × 30 дней и модель срезов §6.4, а не ощущение на текущем объёме. Нормативы — §6.

### 4.2. Атрибуция РК: данные есть, телефония кривая

В `sources` есть `source_name`, `source_phone`, город, макет, format, kind (`flyer`/`party`).

`MangoCallService` **не** ищет по `source_phone`, а читает узкий map из `.env` (`MANGO_LINE_1/2/101_SOURCE_ID`). Другая линия → `source_id = null`.

**Живой факт:** в справочнике у листовок телефоны часто заполнены (`Листовка Алексей` → `9300366894` и т.п.); у многих **Парт / Авито** телефон пустой (`—`). На карточке заказа поле «Источник заказа (РК)» уже есть и работает (пример №295: `СЕРВИС-КАЧЕСТВО · Парты`). В списке заказов РК/DID **не на виду**.

### 4.3. Модуль «Реклама» (`prom.*`) отключён в меню

Код журнала/маршрутов/разноски/оплат есть; в навигации скрыт. Решение по FlyersCrm — §8.5.

### 4.4. GM API частично фасад

Часть полей `null` / пустые коллекции — допустимо поэтапно, но только с явным реестром пробелов, без «тихого вранья».

### 4.5. UI/права (по тестеру и проходу; as-is на 2026-07)

- ОКК для `branch_head`: **as-is частично исправлен** — в меню уже есть «Претензии» + отчёты. Остаётся закрыть приёмкой: просмотр деталей претензии разрешён, **создание запрещено** (§3, §7.3). Если create всё ещё доступен — дефект.
- Список заказов: колонка **РК (`source_name`) уже есть**; нет видимого **номера линии** (`source_phone`) — §7.1.
- Клиенты КЦ: валидация телефонов/адресов и endpoint локального времени города **частично есть**; единый маска-ввод телефона на всех формах — ещё не системно (§5.4, §7.4).
- Отзывы ОКК: нужна жёсткая валидация и нормальные отступы полей.
- Описание заказа: увеличить внутренние отступы textarea (~5); на iOS длинный текст в readonly/disabled полях должен оставаться читаемым (см. §5.13).

## 5. Функциональные требования

### 5.1. Источники заказов (РК) — критический блок

**Поля Source (обязательные по смыслу):**

| Поле | Смысл |
|------|--------|
| `source_name` | Имя РК (на листовке / Авито / канал) |
| `source_phone` | Номер линии клиента (единая нормализация) |
| `city_id` | Город |
| `source_format` | `online` / `offline` |
| `source_kind` | минимум `flyer` / `party` |
| `flyer_maket_id` | макет (для flyer) |
| `is_active` | активность |
| SuperPart-флаги | `available_for_superpart`, `superpart_partner_id`, local id |

**Правила:**

1. Один активный нормализованный `source_phone` = одна РК (уникальность в БД). Допускается таблица алиасов DID → один `source_id`.
2. Канон маппинга линий — **таблица sources**, не `.env`. `.env` только как временный fallback с планом отключения.
3. Для **каждого** боевого DID Mango / Авито / листовки — активный Source с именем и телефоном. Админский отчёт: «линии без РК», «РК без телефона».
4. Импорт CSV/XLSX с валидацией телефонов и уникальности сохраняется.
5. Везде, где видят заказ (список, карточка, дашборд, выгрузки), доступны:
   - название РК;
   - номер линии (`source_phone`);
   - kind/format.

**Приёмка атрибуции:**

- ≥10 тестовых DID → 10 разных `source_name`.
- Webhook/эмулятор Mango на каждый DID пишет верный `calls.source_id`.
- Заказ наследует тот же `source_id`.
- В UI карточки и (после §7.1) в списке заказов РК и номер видны без «угадывания».

### 5.2. Звонки (Mango)

1. Webhook: call / result / record.
2. Входящий: клиентский номер + линия назначения → нормализация → Source → Call.
3. Исходящий: оператор, клиент, длительность, запись.
4. Падение Mango не роняет страницы CRM.
5. В production пустой webhook-secret = отказ обработки.

### 5.3. Заказы

Жизненный цикл не слабее текущего: `pending`, `callback`, `not_processed`, `rejected`, `on_way`, `in_progress`, `in_progress_sd`, `review`, `completed`, `cancelled_cc`, `cancelled_city`, …

Связи: клиент+телефоны, адрес+город, мастер, **source_id**, суммы, тип (впервые/повтор/гарантия), профильность, техника, документы, журнал, просмотр филиалом, sync GM.

Кнопки карточки (as-is, сохранить поведение): Сохранить, Сохр. и закрыть, Копировать, Закрыть, Создать претензию.

### 5.4. Клиенты КЦ

- CRUD клиента, телефоны, адреса, город.
- Единый алгоритм нормализации и **единый UI-ввод** телефона на всех формах (заказы, клиенты, сотрудники).
- Телефон: только цифры (маска), без букв/спецсимволов в поле ввода.
- Улица/дом/квартира: запрет опасных спецсимволов (санитизация); допустимы буквы, цифры, пробел, дефис, корпус/строение по правилам валидации.
- При выборе города — показ **локального времени** клиента (TZ города уже в справочнике).

### 5.5. Касса (CFM)

Операции, категории, закрытие/переоткрытие, документы, расчёт мастера, отчёты, связь с заказом (`related_order_id`).

### 5.6. Сотрудники (HR)

CRUD, роли, города, увольнение/восстановление, blacklist, документы/верификация паспорта, рейтинг, график (roster), выдача учёток GM без обратимого хранения паролей сверх политики §9.

### 5.7. ОКК

- Претензии: список, карточка, отчёт; права — §3.
- Отзывы (КЦ): сущность = ссылка (одна строка) + картинка (с превью) + ID партнёра + номер заявки; валидация без опасных спецсимволов; понятно «от кого / на кого».

### 5.8. Управление

Города (TZ МСК±N, parent, активность), макеты листовок, источники (§5.1), кассовые категории. Закрепление времени — отдельный рабочий раздел (уже в меню).

### 5.9. Дашборд диспетчера

KPI за скользящие 7 дней, фильтры город/мастер/формат/источник, таблица с колонкой источника. Лёгкие count-запросы; без лишней нагрузки.

### 5.10. Уведомления филиалу

Счётчик/список непросмотренных заявок, опрос API, browser notifications — сохранить; оптимизировать нагрузку при росте.

### 5.11. База знаний

Статьи с видимостью по ролям.

### 5.12. Отчёты (состав)

Не слабее текущего меню:

- По закрытым заявкам;
- По городу (сотрудник);
- Оборот мастеров;
- Статистика заявок;
- Отмены и отказы;
- Партнёры;
- плюс кассовые/ОКК-отчёты в своих разделах.

Все — по правилам производительности §6.

### 5.13. Операционные инварианты (не ломать)

Зафиксированы по эксплуатации 2026-07; регресс = дефект приёмки этапа C (и регрессионные smoke после A/B):

1. **Спутник → 50/50:** заказ в городе-спутнике (`parent_city_id` задан) и/или с явной семантикой спутника получает профильность «прочий» (50/50) по действующим правилам; CFM после правок пересчитывается согласованно.
2. **Дальний выезд:** галочку ставят/снимают только `call_center` и `senior_dispatcher`.
3. **Поиск заказа:** по ID / адресу / телефону **не режется** сессионным архивным окном месяца, если пользователь явно ищет конкретную заявку.
4. **Мобильная карточка:** длинные textarea (описание, переносы) на iOS читаемы и прокручиваются (`readonly`, не «мёртвый» `disabled` без скролла).
5. **Группировка городов:** `parent_city_id` — канон для спутников; особый случай «только Н. Новгород» в коде считается техническим долгом к выравниванию, не бизнес-исключением навсегда.

## 6. Производительность

### 6.1. Нормативы (p95)

| Сценарий | Норматив | Нагрузка приёмки |
|----------|----------|------------------|
| Список заказов (месяц, 1–3 города) | ≤ 1.5 с TTFB | 30 сессий |
| Карточка заказа | ≤ 800 мс | 30 сессий |
| Отчёт по городам, ≤80 городов, месяц | ≤ 3 с полный ответ агрегатов | 10 параллельных отчётов |
| Отчёт ≤200 городов, месяц | ≤ 8 с **или** очередь + готовый файл/кэш ≤ 60 с | то же |
| Mango webhook → Call | ≤ 300 мс ack | 20 rps |
| `/api/v1/health` | ≤ 100 мс | постоянно |

Базовая цель одновременных пользователей: **≥ 50**. Точное N роста — уточняет заказчик.

### 6.2. Обязательные меры

1. Запрет «цикл по городам + `get()` всех заказов» в отчётах.
2. Агрегации в SQL; для отчётов руководителя — материализованные срезы (§6.4).
3. Индексы: `orders(order_created_at)`, `(order_status, order_closed_at)`, `source_id`, `addresses.city_id`, `sources.source_phone`, `calls(call_created_at, source_id)`.
4. Большой CSV — только через очередь.
5. Кэш справочников (Redis предпочтительно; на shared до VPS — file/database cache допустим).
6. Outbound GM/SuperPart/Mango API — асинхронно, если ответ не нужен для отрисовки экрана.

### 6.3. SPA / PostgreSQL

Не блокеры. Тяжёлые экраны обязаны уметь отдавать лёгкие JSON/агрегаты. SPA/Postgres — этап при необходимости.

### 6.4. Материализованные отчёты и инвалидация (обязательная модель)

Без этой модели этап B считается непринятым.

**Таблица срезов (имя может отличаться, смысл обязателен):** `report_city_daily` (или эквивалент).

| Поле / смысл | Требование |
|--------------|------------|
| Зерно | 1 строка = город + календарный день (+ при необходимости разрезы: source_format / «наш/партнёр») |
| Метрики | не слабее текущего отчёта «по закрытым» / статистики: принято, закрыто, наши/партнёры, оборот, чистыми, претензии, promo/цена заявки — по фактическим колонкам отчётов |
| Идемпотентность | повторный пересчёт дня даёт тот же результат |

**Кто пишет срез:**

1. **Ночной job** — полный пересчёт вчерашнего дня + «догон» текущего месяца (обязателен).
2. **Событийная инвалидация** — при событиях, меняющих метрики дня: закрытие/переоткрытие заказа, смена сумм закрытого заказа, проведение/отмена кассовой операции, влияющей на отчёт, смена `source_id` у заказа в закрытом периоде. Инвалидация = пометка дня/города `stale` + постановка в очередь пересчёта (не синхронный тяжёлый пересчёт в HTTP-запросе пользователя).

**Что видит пользователь:**

- Экран отчёта читает **срезы**, не сырые `orders` пачкой.
- Если срез `stale` или отсутствует: либо показать данные с меткой «обновляется…» и досчитать в фоне ≤ норматива §6.1, либо для малого периода (1–3 города, ≤7 дней) допустим live SQL-агрегат без среза.
- Запрещено снова скатывать весь месяц всех городов в PHP ради одного открытия страницы.

**Приёмка §6.4:** фикстура ≥80 городов × 30 дней; открытие отчёта за месяц ≤ 3 с p95; после закрытия тестового заказа срез города за день становится `stale` и обновляется job’ом без ручного вмешательства.

### 6.5. Мониторинг и алерты (NFR)

Обязательный минимум (на shared — упрощённо через логи + health; на VPS — полноценно):

| Сигнал | Условие алерта |
|--------|----------------|
| `GET /api/v1/health` (или `/up`) | недоступен > 2 мин |
| Время отчёта руководителя | p95 за час > норматива §6.1 |
| Mango webhook | доля 5xx / отказов > порога или 0 успешных при ожидаемом потоке |
| Очередь (report rebuild / outbound sync) | рост backlog > N минут без разбора |
| Бэкап | ночной бэкап не создан / не прошла проверка манифеста |
| Диск / storage | свободное место < порога |

Алерты — на канал, доступный заказчику/админу (почта / мессенджер / панель). Без мониторинга этап F не закрывается.

## 7. Требования к интерфейсу (по живому проходу + тестер)

Общий визуальный язык as-is сохраняем (тёмная шапка LC, фиолетовый акцент, светлая/тёмная тема). Полный редизайн не требуется.

### 7.1. Список заказов

1. **As-is:** колонка **РК (`source_name`)** уже есть. **Обязательно добавить** видимый **номер линии** (`source_phone` источника) или эквивалент без горизонтального «угадывания».
2. Сохранить CTA «Создать заказ», фильтры, подсветки типов/дат, пагинацию, «открыть в новой вкладке».
3. На мобильной ширине: ключевые действия и РК **не прятать** без доступа (номер линии — по возможности; минимум РК обязателен).

### 7.2. Карточка заказа

1. Поле «Источник заказа (РК)» — обязательно, подпись в селекте: имя · город · телефон · формат/kind (как сейчас для листовок).
2. Кнопки действий всегда доступны (не обрезаны сайдбаром на типичных разрешениях 1366×768 и 1920×1080).
3. Textarea «Описание заказа» — внутренние отступы ≥ эквивалента **5** (замечание тестера).
4. Блоки: просмотр филиалом, клиент, документы, история — сохранить.

### 7.3. ОКК

1. Для `branch_head`: в меню ОКК — **Претензии** + **Отчёты** (меню as-is уже близко к цели). Приёмка: детали претензии — **просмотр**; **создание — запрещено**. Если create доступен — закрыть правами.
2. Отзывы / «Обратная связь»: поля ссылка / картинка+превью / ID партнёра / номер заявки; без опасных спецсимволов.

### 7.4. Клиенты КЦ и телефоны

1. Локальное время города при создании записи после выбора города.
2. Единый компонент ввода телефона на всех формах.
3. Валидация телефонов и адресов — §5.4.
4. Навигация раздела «Клиенты КЦ» — привести к согласованному виду (по макету тестера, когда будет приложен визуал; до макета — единый стиль с остальной CRM).

### 7.5. Источники

1. Вкладки Все / Листовки / Парты / SuperPart, Импорт, Добавить — сохранить.
2. Подсветка/фильтр «без телефона» для админа.
3. Строка списка ведёт в редактирование (как сейчас) — допустимо; либо явная кнопка «Изменить».

### 7.6. Отчёты и дашборд

1. Фильтры периода/города, быстрые пресеты, «Скачать», «Поиск» — сохранить.
2. Дашборд: фильтр по источнику обязателен (уже есть) — не ломать.
3. Подсказки под таблицами (наши/партнёры/чистыми) — сохранить смысл.

### 7.7. Tooltips

На всех ключевых кнопках и неочевидных иконках (П/Н, открыть в новой вкладке, сброс фильтров, тема) — понятные подсказки при наведении.

### 7.8. Что не ломать без отдельного решения

Цветовые маркеры строк, sticky-фильтры таблицы заказов, уведомления о новых заявках филиалу, расчёт «к сдаче» / доля мастера на карточке.

## 8. Интеграции

### 8.1. Общие правила

1. Свой ключ/секрет на интеграцию, минимальные права.
2. Валидация + санитизация входящих данных.
3. Timeout, retry с backoff, идемпотентность где нужно.
4. Падение внешней системы не увеличивает TTFB списка заказов > 20%.
5. Логи интеграций + audit (§9).

### 8.2. Mango

Webhook `/api/mango/webhook`; атрибуция DID→Source (§5.1–5.2); click-to-call сохраняется.

### 8.3. SuperPart

`/api/v1/...` с `X-API-Key` + `X-Signature`. Права: заявки + справочники по контракту; **без** произвольного чтения всей клиентской базы. `source_id` проверяется; default source — временный fallback.

### 8.4. GM

Bearer `/api/v1/gm/*`; sync пользователей/заказов/документов; реестр недостающих полей ведётся явно.

### 8.5. FlyersCrm / promo

CRM владеет «номер → РК → заказ». Решение: включить `prom.*` в Lead Control **или** оставить FlyersCrm — продуктовое решение **этапа G**.  
**Дедлайн решения:** не позднее **14 календарных дней** после старта этапа A (фиксируется письменно / в трекере). До решения атрибуция звонков в CRM (§5.1–5.2) обязана работать независимо от FlyersCrm.

### 8.6. Внешние таблицы менеджеров («Виртус Пром» и аналоги)

Только API/очередь; прямой SQL снаружи к БД CRM запрещён.

## 9. Безопасность и криптография

### 9.1. Принципы

Безопасность не убивает §6. Тяжёлая криптография — на границах и чувствительных артефактах. Секреты не в git.

«ГОСТ 31.10» в исходных формулировках = **ГОСТ Р 34.10-2012**.

### 9.2. Транспорт

- HTTPS, целевой TLS 1.3, редирект 80→443, HSTS.
- Массовые браузеры: совместимые cipher suites (AES-GCM / ChaCha20-Poly1305).
- ГОСТ-TLS (RFC 9367) — **опциональный** контур для СКЗИ/внутренних клиентов, не единственный способ входа менеджеров.

### 9.3. AEGIS (прикладной AEAD)

| Профиль | Назначение |
|---------|------------|
| **AEGIS-256** | Бэкапы, архивы ПДн, секретные поля at-rest, payload очередей с ПДн |
| **AEGIS-128L** | Короткоживущие токены/кэш-blobs, где критичен поток |

Уникальные nonce; ключи отдельно от шифротекста; ротация ≥ раз в 12 месяцев или при компрометации; только проверенные реализации.

### 9.3.1. PoC криптографии (обязателен до боевого внедрения §9.3–9.4)

**Важно для порядка работ:** PoC и боевое внедрение AEGIS/ГОСТ **не блокируют** приёмку этапов **A–C**. Целевая площадка PoC — **staging VPS** (или VPS после старта F). На shared допустим временный контур бэкапов ISP / AES-256-GCM без ГОСТ-подписи, с ADR и сроком замены после VPS.

До шифрования боевых бэкапов AEGIS/ГОСТ на проде:

1. Провести **PoC на целевом PHP 8.2** (предпочтительно staging VPS; shared — только если VPS ещё нет): encrypt/decrypt тестового архива AEGIS-256; подпись/проверка манифеста ГОСТ Р 34.10-2012 (+ Стрибог); замер времени на типичном размере бэкапа.
2. По результату PoC зафиксировать **конкретные библиотеки/расширения** в коротком ADR (не в этом ТЗ до PoC — чтобы не закрепить нерабочий стек).
3. Критерий PoC: операция ночного бэкапа не сдвигает окно обслуживания неприемлемо (ориентир: шифрование+подпись тестового дампа ≤ нескольких минут на ожидаемом объёме; точная цифра — в ADR после замера).
4. Если AEGIS/ГОСТ-библиотека на платформе нестабильна — временный контур: AES-256-GCM для архива + ГОСТ-подпись манифеста **только** с явным ADR и сроком замены.

### 9.4. ГОСТ Р 34.10-2012 (+ ГОСТ Р 34.11-2012 «Стрибог»)

Подпись манифестов бэкапов, audit-экспортов, критичных интеграционных пакетов; при необходимости VKO между своими сервисами.

Симметричный ГОСТ-контур при регуляторной нужде: **ГОСТ Р 34.12-2015 «Кузнечик»**. Если overhead неприемлем на high-load — AEGIS-256 + ГОСТ-подпись манифеста (ADR).

### 9.5. Пароли, сессии, brute-force

- Argon2id (предпочтительно) или bcrypt; запрет обратимого хранения паролей.
- После 5 неудачных попыток — блок 15 минут (IP и/или учётка).
- Cookie: `Secure`, `HttpOnly`, `SameSite` (≥ `Lax`; `Strict` где не ломает сценарии).
- 2FA TOTP обязательна для `developer`, `general_director` и ролей с экспортом/управлением источниками; для остальных — по политике заказчика (рекомендуется всем ≤ 60 дней после внедрения).

### 9.6. RBAC, IP allowlist, ключи

RBAC §3; крупный экспорт ПДн — только gen.dir/developer (уточняемая матрица). Опциональный IP allowlist для admin. Ключи Mango/GM/SuperPart — раздельные, с ротацией.

### 9.7. Аудит и ФЗ-152

Журнал: вход, просмотр/изменение ПДн, экспорт, действия интеграций (кто/когда/IP/токен). Без редактирования рядовыми. «Право на забвение» ≤ 30 дней по регламенту. Хранение ПДн в РФ.

### 9.8. Инфраструктура REG.RU и обязательный VPS

**Сейчас (shared):** `.env` вне web-root; HTTPS; бэкапы ISP; не светить лишние панели. На shared допустимы и **сдаются** этапы **A–C** (атрибуция, отчёты, UI) без ожидания PoC §9.3.1 / cutover VPS. Этап **B** на shared обязан уложиться в §6.1 на доступном объёме; полная приёмка 80×30 — на staging/VPS при необходимости.

**Целевое (VPS в РФ, REG.RU) — обязательно**, не «по желанию»:

| Требование | Деталь |
|------------|--------|
| Срок | Перенос на VPS **не позднее 60 календарных дней** после старта этапа A (или раньше, если §6.1/§6.5 не держатся на shared) |
| Что не блокирует | Старт и сдача этапов **A и B** на текущем хостинге разрешены |
| Сеть | Снаружи только 80/443; SSH по ключу (желательно VPN/Tailscale); порт БД закрыт |
| Runtime | PHP 8.2+, очередь worker, Redis (или эквивалент), cron |
| Бэкапы | Ежедневно, хранение ≥ 30 дней; архив **AEGIS-256** (после PoC §9.3.1); манифест **ГОСТ Р 34.10** |
| Мониторинг | §6.5 на VPS в полном объёме |

План переноса (кратко): staging VPS → миграция БД/файлов по §10 → DNS/SSL → проверка health и отчётов → cutover → старый shared только как read-only/бэкап на период отката ≤ 14 дней.

## 10. Миграция данных и поставка

### 10.1. Общие правила

1. Только миграции Laravel (или эквивалент со следом в репо); запрет «тихих» правок прод-БД без скрипта.
2. Перед каждой боевой миграцией — бэкап БД + проверка, что бэкап открывается.
3. Секреты не в git; доступы уволенного подрядчика отозваны; секреты ротированы **до** активной разработки с новыми ключами.
4. Деплой воспроизводим (скрипт/CI), не хаотичный FTP без списка файлов.
5. Минимум автотестов (**обязательный DoD этапов A/B/C**): DID→Source; агрегат/срез отчёта на фикстуре ≥80 городов; throttle логина.  
   **Рекомендуется (не блокирует A–C):** подпись SuperPart; права `branch_head` на ОКК; smoke операционных инвариантов §5.13.

### 10.2. Пошаговый план миграции данных (критичный)

Порядок **обязателен**; каждый шаг — с проверкой «до/после» и возможностью отката на бэкап шага.

| Шаг | Действие | Проверка | Откат |
|-----|----------|----------|-------|
| 0 | Полный бэкап БД + `storage` | Файл бэкапа есть, размер > 0 | — |
| 1 | Инвентаризация: активные DID Mango, `sources` без телефона, дубли телефонов, ненормализованные `person_phones` | Отчёт-CSV «дыры» сохранён | — |
| 2 | Миграция схемы: алиасы линий (если нужны), поля срезов отчётов, индексы §6.2 | `migrate` на копии БД OK | rollback migration |
| 3 | Нормализация телефонов в `sources.source_phone`, `person_phones`, связанных полях calls (единый формат) | Выборочная сверка 20 номеров; уникальность активных source_phone | восстановить из бэкапа шага 0/3 |
| 4 | Заполнение/починка РК: каждой боевой линии — активный Source; ручная сверка с заказчиком по именам на листовках/Авито | 0 «боевых линий без РК» | точечный SQL из бэкапа строк sources |
| 5 | Отключение канона `.env` line_sources (оставить только fallback→лог предупреждений) | Тестовые webhook на 3+ DID → верный source_id | вернуть чтение env |
| 6 | Первичный backfill `report_city_daily` за текущий + прошлый месяц | Отчёт за месяц сходится с контрольной ручной выборкой по 3 городам | truncate срезов + пересчёт |
| 7 | (Этап F) Перенос на VPS: dump/restore, файлы, `.env`, DNS | health, логин, отчёт, webhook test | DNS назад + shared |

**Запрещено** на шагах 3–5: менять статусы/суммы заказов «заодно». Миграция касается идентификаторов, телефонов, источников и срезов, не бизнес-перепроведения заказов.

## 12. Критерии приёмки (сводка)

Приёмка разделена на **MVP (блокирует бизнес-релиз A–C)** и **gate E/F** (security/инфра). Пункты gate E/F **не** блокируют сдачу атрибуции и отчётов на shared.

### 12.A. MVP — этапы A–C (обязательно)

1. Отчёт на ≥80 городах за месяц — по §6.1 **и** модель §6.4 (этап B).
2. 100% активных боевых линий имеют Source; тестовые звонки дают верный `source_name` в Call и заказе (этап A).
3. В списке и карточке заказа видны РК и номер линии (A + §7.1).
4. `branch_head` видит претензии (без создания) + отчёты ОКК (C).
5. Телефоны на ключевых формах — единый числовой ввод; локальное время города при создании записи КЦ (C).
6. Падение SuperPart/GM/Mango не раздувает TTFB списка заказов > 20% (минимум на shared; полное — с D).
7. Выполнен план миграции §10.2 шаги 0–6 (зафиксированы логами/чеклистом).
8. Нет обратимых паролей; throttle логина работает; Mango webhook без секрета в prod не принимается (базовый security, без AEGIS).
9. Доступы уволенного подрядчика отозваны; секреты ротированы (орг. до активной разработки).
10. Замечания тестера из `_source_tester_CRM_Lead_Control.txt` закрыты или явно перенесены в известный дефект с датой.
11. Операционные инварианты §5.13 не регресснули (smoke).

### 12.B. Gate E/F — security и инфра (не блокирует MVP A–C)

12. PoC крипты §9.3.1 принят; ночной бэкап: AEGIS-256 (или временный ADR-контур) + манифест ГОСТ Р 34.10; restore на staging проверен.
13. Мониторинг §6.5: health и алерт на падение бэкапа/отчёта настроены (на VPS — полный набор).
14. VPS: либо уже в проде, либо не просрочен срок §9.8 с утверждённым планом cutover.
15. 2FA для критичных ролей (§9.5) включена по политике этапа E.

## 13. Открытые вопросы (не блокируют утверждение ТЗ)

1. Точное целевое N одновременных пользователей и число городов у «самого широкого» регдиректора — **нужны цифры заказчика** (без них §6.1 спорят при нагрузке). До ответа ориентир приёмки: N ≥ 50 (§6.1), отчёт ≤80 / ≤200 городов как в таблице.
2. Полный реестр боевых DID Mango ↔ имена на листовках/Авито (заполняется на этапе A; старт A не ждёт полного реестра — итеративно).
3. Оставляем FlyersCrm или включаем `prom.*` — решение за **14 дней** после старта A (§8.5).
4. Срок обязательного 2FA для всех ролей (критичные — в этапе E; остальные — политика заказчика).
5. Нужен ли отдельный ГОСТ-TLS контур со СКЗИ (по умолчанию — нет, dual-контур §9.2).
6. Финальный визуал навигации «Клиенты КЦ» от тестера (если будет отдельный макет).
7. Список плательщиков/получателей директорских операций CFM (парты / Уровень / инкассация) — продуктовое уточнение вне критического пути A/B.
