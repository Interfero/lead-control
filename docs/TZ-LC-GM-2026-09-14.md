## 1. Закрытие из СД — 500 (блокер)

Кабинет закрывает так:

`POST /api/v1/gm/orders/578/review` + заголовки мастера #112

```json
{
  "amountPaidRub": 5000,
  "amountCompRub": 0,
  "masterComment": "отписка"
}
```

CRM отвечает HTTP 500 `{ "message": "Server Error" }`.
Статус не меняется: `in_progress_sd`.

Пустой POST на тот же URL — 422 (нет сумм и отписки). Маршрут живой. Падает проведение.

То же 500 на 2281488 / 1488 и на 5000 / 0 — не в сумме.

POST `…/in-progress` из СД — честные 422 `invalid_status_transition`.
POST `…/complete` и `…/close` — 404. Закрытие только через review.

Лог CRM: 2026-09-14 ~11:40 МСК.

Нужно: review закрывает и `in_progress`, и `in_progress_sd`. После СД мастер закрывает заявку — это нормальный поток.

Успех: статус как в веб-CRM при закрытии, суммы + `financialSnapshot`, отписка в комментарий филиала блоком «Отписка мастера при закрытии заявки», HTTP 2xx, в JSON есть `order.status`.

Если закрыть нельзя — не 500, а 409/422 с кодом.

Тело не меняем: `{ amountPaidRub, amountCompRub, masterComment }`, заголовки мастера заявки.

Приёмка на #578:

- GET `/orders/578` с `X-GM-User-Id: 112` → `in_progress_sd`.
- POST `…/review` с телом → не 500, статус уже не СД.
- Повтор на закрытую → 409, не 500.
- В laravel.log нет unhandled exception.
- Кабинет этот контракт уже шлёт.

## 2. Время визита scheduledAt

В веб-CRM правят время визита (`datetime_order`). Кабинет этого поля не видит и рисует `createdAt` — время создания. Пока заявку только завели, они совпадают. После переноса визита кабинет остаётся на старом времени.

На #578 (prod, 2026-09-12):

| Что | Значение |
|-----|----------|
| `createdAt` в GET `/orders` и GET `/orders/578` | `2026-09-12T13:39:16+03:00` |
| `datetime_order` / `scheduledAt` в ответе | нет такого ключа |
| Журнал заявки | есть событие «Перенос встречи» |

`createdAt` после переноса не меняется — это нормально. Нужно отдельное поле.

В list GET `/orders` и detail GET `/orders/{id}`:

```json
"scheduledAt": "2026-09-12T16:44:00+03:00"
```

Источник: то же, что диспетчер видит/правит как время заявки (`datetime_order`).
Формат: ISO-8601 с поясом, как у `createdAt` / `statusChangedAt` / `inProgressAt`.
После каждого переноса визита в CRM новое значение в следующем GET.
`createdAt` не трогать.
Если времени визита нет — `scheduledAt: null`, не подставлять `createdAt`.
В `docs/API.md` на стороне LC коротко описать поле.

Приёмка:

- GET `/orders` и GET `/orders/578` с `X-GM-User-Id: 112` содержат `scheduledAt`.
- В LC перенести визит на #578 → тот же GET отдаёт новое время, `createdAt` остаётся `13:39:16+03:00`.
- Поле есть у `pending` / `on_way` / `in_progress` / `in_progress_sd`, не только в detail.
- После выкладки — кабинет подключает за несколько минут.

## 3. Претензии — как устроено + минимум API

В кабинете нужен флаг «есть претензия по заявке» (и по возможности статус/краткий текст). Не путать с отзывом мастера / POST `…/review` / `users/me/reviews`.

Сейчас в GET `/orders` и detail нет claim-полей. Пробные URL `/claims` на gm / desk / корень API → 404.

Вопросы (можно пунктами):

- Сущность: отдельная таблица или флаг на заказе?
- Связь с заявкой: 1:1 / 1:N / N:M? Обязателен ли `order_id`? Бывает претензия без заявки?
- FK: клиент / НК / мастер / филиал — что обязательно?
- Жизненный цикл: статусы, кто создаёт/закрывает (роли)?
- Претензия vs «отзыв НК» vs негатив — одно или разные сущности/экраны?
- Поля: текст, сумма, причина, вложения, ответ, даты?
- Веб-маршруты CRM: URL / контроллеры экрана.
- Есть ли уже любой JSON (desk/crm) по `order_id`? Путь и пример ответа.
- Права: мастер своей заявки / директор / только НК?
- Несколько претензий на одну заявку за жизнь?

Минимум API, если внешнего ещё нет. Вариант A (лучше для списка) — в GET `/orders` и GET `/orders/{id}`:

```json
{
  "hasClaim": true,
  "claim": {
    "id": 123,
    "status": "open",
    "createdAt": "2026-09-01T12:00:00+03:00",
    "summary": "кратко, опционально"
  }
}
```

`hasClaim`: boolean — обязательно.
`claim` / `claims[]` — если удобно отдать снимок; иначе достаточно `hasClaim`.
Вариант B: GET `/orders/{id}/claims` (пустой массив = нет).

Приёмка: без претензии — false / []; с претензией — стабильно true / непустой список; мастер видит только свои заявки; enum статусов в `docs/API.md`.
