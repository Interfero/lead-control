# Заказ REG.RU VPS для этапа F (ТЗ §9.8)

**Цель:** prod CRM на **VPS REG.RU в РФ**, не shared и не Selectel.

**Решение по мощности (2026-07-23):** целевое **4 vCPU / 8 GB / 80 GB**.  
**Факт VPS (доступ есть):** IP **`194.67.92.69`**, SSH host `reg-vps`, Ubuntu **22.04**, **8 vCPU / ~8 GB RAM / ~119 GB SSD** — выше рекомендации.

Ориентир по prod shared сейчас: БД ~4 MB, код+storage ~0.5 GB, ~140 users / ~230 orders; calls пустые (Mango ещё не включён). Запас нужен под рост, §6.1 и ночные бэкапы — не под «сегодняшние 4 MB».

## Что заказать в панели REG.RU

| Параметр | Значение |
|----------|----------|
| Локация | **РФ** |
| OS | Ubuntu **22.04** LTS (допустимо 24.04) |
| CPU | **4 vCPU** |
| RAM | **8 GB** |
| Диск | **80 GB SSD** |
| Сеть | Публичный IPv4 (+ IPv6 по желанию) |
| Доступ | **root** по SSH-ключу |

PHP на VPS ставим сами (**8.2+**, на shared сейчас 8.2.31).

Минимальный запасной вариант 2/4/40 — только если бюджет жёстко режет; для CRM + Redis + бэкапы **не рекомендуем**.

## Для чего такие мощности (разбор)

### 4 vCPU — параллельные задачи

На одной машине одновременно:

| Процесс | Зачем CPU |
|---------|-----------|
| **Nginx + PHP-FPM** | Страницы CRM: заказы, касса, отчёты (ТЗ: до ~50 сессий, отчёт ≤80 городов ≤3 с) |
| **MariaDB** | Агрегаты отчётов, срезы `report_city_daily`, поиск клиентов |
| **Redis + queue worker** | Фоновые job’ы GM / SuperPart / rebuild срезов — не блокируют UI |
| **Cron + backup:encrypt** | Ночью шифрование дампа (AEGIS) + verify — тяжёлая одноразовая нагрузка |
| **Mango webhook** | Короткие всплески (ориентир ТЗ до ~20 rps ack) |

**2 vCPU** хватит «пока тихо»; при отчёте + webhook + worker + бэкап всё конкурирует за одни ядра → тормоза UI. **4 vCPU** — запас, чтобы отчёт и фон не душили операторов.

### 8 GB RAM — чем живёт стек

| Компонент | Ориентир |
|-----------|----------|
| OS + Nginx | ~0.3–0.5 GB |
| PHP-FPM (несколько воркеров) | ~1.5–3 GB под пик сессий |
| MariaDB (буфер + кэш) | ~1.5–2.5 GB |
| Redis (cache + queue) | ~0.3–0.8 GB |
| Supervisor worker + cron PHP | ~0.2–0.5 GB |
| Пик бэкапа / migrate | +1–2 GB кратковременно |
| **Итого в пике** | **~6–7 GB → нужны 8 GB с запасом** |

**4 GB** = PHP+MySQL съедят почти всё, начнётся swap → медленный CRM. **8 GB** — БД и кэш в памяти.

### 80 GB SSD — данные и история

| Что лежит | Зачем место |
|-----------|-------------|
| Код Laravel + vendor | ~0.2–0.5 GB |
| `storage` (вложения, логи) | сейчас ~0.4 GB → рост с фото/документами |
| MariaDB data | сейчас ~4 MB → рост заказов/звонков |
| **Бэкапы ≥30 дней** (ТЗ §9.8) | дампы + AEGIS — главный потребитель диска |
| Staging на том же VPS (до cutover) | вторая копия для smoke |
| Система, логи | запас |

**40 GB** — «приложение + пара бэкапов». **80 GB** — месячный архив бэкапов + staging без чистки впритык.

### Почему не меньше «раз БД 4 MB»

Мощности считаем не по размеру БД сегодня, а по **рантайму**: PHP + MySQL + Redis + очереди + шифрование + целевая нагрузка ТЗ. Маленькая БД ≠ маленькая RAM.

## Что прислать разработке после заказа

1. **IP** VPS  
2. Способ входа: `root@IP` + ключ уже добавлен **или** одноразовый пароль  
3. Подтверждение: firewall не режет 22/80/443  

```
Host reg-vps
    HostName <IP>
    User root
    IdentityFile ~/.ssh/id_ed25519_reg
```

## Что сделаем после доступа

1. `deploy/vps/provision-regru-ubuntu.sh` — Nginx, PHP 8.2, MariaDB, Redis, UFW, Supervisor, cron  
2. Staging на том же VPS  
3. Пробный dump shared → restore  
4. PoC `backup:encrypt` / `backup:verify`  
5. Окно cutover (DNS) — отдельный день  

См. `docs/CUTOVER-PLAN.md`, `docs/CUTOVER-DAY-X-RUNBOOK.md`, `docs/OPS_STAGE_F.md`.
