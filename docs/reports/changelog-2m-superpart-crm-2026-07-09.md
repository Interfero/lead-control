## SuperPart — что меняли

### Деньги и начисления (24–28.08 + догон)

- CRM `completed` больше **не** превращается в «Отказ» без начисления.
- Формула партнёру: **30% от (оплата − комплектующие), потолок 2500 ₽**.
- Кошелёк = владелец заявки в SP (`orders.user_id`); webhook допускает пустой `partner_user_id`.
- Страховка: cron `orders:reconcile-crm` **каждые 5 мин**.
- Бэкап ложных отказов ~**38 111 ₽** (сверка с CRM).
- Баланс на главной = леджер; «Выплачено за месяц» = **с 1 числа**, не за всё время.
- Дублей charge и пересечений с уже выплаченными — нет (на момент аудита).

### Источники и видимость заявок

- Новые источники партов — **общие** (`shared_with_all_partners`), в CRM для webhook снова нужен **owner**.
- После 25.08 заявки «пропали» из‑за обнуления `superpart_partner_id` → починено, догон до **#507**, 43/43 OK.
- Колонка «Источник» в списках; timezone `Europe/Moscow`.
- **09.09:** видимость заявки/начисления в списках партнёра только пока РК **в каталоге SuperPart**; смена на «Листовку» и т.п. → скрыть (charge в БД не удаляем). Cron remapping ~**10 мин**.
- Elevated видит всё.

### Менеджеры (08.09)

- У менеджеров **нет** баланса/кошелька в навбаре.
- Отчёт по заявкам только по **прикреплённому партнёру** (без окна 7 дней «как у партнёра»).
- В отчёте менеджера **скрыты** начисления (карточка/колонка/экспорт).
- Прямой `/transactions` → 403.

### Отчёты / UI (08.09 и ранее)

- Экспорт заявок в Excel с периодом и фильтрами; серверная сортировка; лимит выгрузки ~10 000 строк.
- Тайлы дашборда с суммой 0 ₽ — не баг (нет своих заявок/начислений).

### Защита тестовых учёток (09.09)

- Таблица `agent_account_locks` для `#8/#9/#10` (`partner@…`, `manager@…`, `teststarsh@…`).
- Агент не меняет пароль/профиль без явного разрешения; UI человеку можно.
- **Критичный фикс:** поле `balance` **не** должно блокировать CRM-начисления (иначе webhook 500, как у заказа **542**).

### Синк 521/542 (09–10.09)

- **542:** был `in_work` без charge из‑за лока balance → после фикса `waiting_payment`, charge **450**.
- **521:** сначала complete при `source_id=null` → 404; после назначения SP-РК появился + charge (cap 2500).
- House в webhook может быть пустым (дефолт «б/н»).
- Unit-тесты sync/guard/visibility: **7/7 PASS** на prod.

### Прочее

- Login throttle/lockout **только по email** (VPN/NAT) — в LC; SP на `testir.space`.
- AI-Memory onboarding, хаб продукта (роли/заявки/деньги/источники), короткие записи после задач.

## Lead Control (CRM) — что меняли

### Стык с SuperPart (критично)

- Sticky `partner_user_id` **сбрасывается**, если РК больше не SuperPart.
- При смене РК на SP → сразу `notifyPartnerOrderCreated` (**`dispatchSync`**, не ждать queue).
- При уходе с SP → force-notify со старым partner, чтобы SP перемапил источник.
- Если заказ уже **closed/completed** и назначили SP-РК → сразу ещё и `NotifySuperpartOrderCompletedJob`.
- При `order-completed` **404** → сначала create, потом charge.
- Deploy правок синка — на **VPS** `/var/www/lead-control`, не на shared twin.

## Жёсткие правила «не ломать» (для ТЗ)

1. **Начисление:** 30% (paid−parts), cap **2500**; кошелёк = владелец заявки в SP.
2. **Reconcile** `orders:reconcile-crm` каждые 5 мин — не отключать без замены.
3. **Видимость РК:** заявка у партнёра только при `available_for_superpart`; charge не удалять при смене на Листовку — только скрывать.
4. **Локи учёток 8/9/10:** не трогать пароль/профиль скриптами; **balance для CRM webhook должен проходить**.
5. **Прод CRM = VPS**, не shared hosting twin.
6. Notify create/complete в идеале **синхронно** (`dispatchSync`), иначе задержки/«не появилось сразу».
7. Менеджер: без баланса и без колонки начислений; scope только свой партнёр.
8. Id заявки в SP = id CRM.
9. Секреты/пароли не писать в git, vault, конспекты.
